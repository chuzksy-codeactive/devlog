# Building DevLog — running journal

Kept in the exact shape of a DevLog Sprint Journal entry (Problem / Solution / Technical Design / Challenges / Result), since the plan is to eventually publish "building DevLog" as a real entry on Chika's own DevLog portfolio once it launches — using the product to document its own creation. ## Title (draft)

Building DevLog: a developer career operating system, from architecture review to first working auth.

## Delivered so far

Sprint 0: multi-tenant schema, row-level security, and Clerk authentication, end to end and proven. Milestone 2: Sprint Journal entry creation plus the write-time anonymization pipeline, backed by Anthropic. Milestone 3: the first real UI — Home and Experience pages. Milestone 4: the embedding pipeline and a real, working Ask AI, plus a configurable LLM generation provider and a full framework upgrade to .NET 10. Milestone 5: Request Interview — the last Phase 1 core feature, closing out the MVP roadmap's feature table. Milestone 6: email integration — Postmark-backed creator notification on new interview requests.

## Problem

Standard developer portfolios (a CV, a skills list, a GitHub link) show *what* a developer knows but not *how* they work — the exact evidence a recruiter needs to decide whether to book an interview. The idea: a "developer career operating system" where sprint-level case studies and an AI assistant let recruiters query real technical decisions directly, anonymized so no employer confidentiality is at risk.

## Solution

A multi-tenant SaaS (ASP.NET Core + Postgres + Clerk + Next.js) where each developer gets a portfolio with an Experience timeline, a Sprint Journal of case studies, a Learning Lab, and a persistent AI assistant recruiters can query — all sitting on a write-time anonymization pipeline that sanitizes and requires human approval before anything is public.

## Technical design

- **Tenant isolation enforced twice**: application middleware sets tenant context from a verified Clerk JWT claim, and Postgres Row-Level Security independently refuses cross-tenant rows even if application code has a bug — proven with a test that queries deliberately without a `WHERE tenant_id` clause and confirms RLS alone blocks the leak.
- **Raw and sanitized content are physically separate tables**, not a status flag, so there is no code path — buggy or not — that can expose an unsanitized draft.
- **Clerk over Auth0** for authentication, chosen primarily on cost at the expected mostly-free-tier user volume, accepting a less conventional JWT validation pattern (`azp` claim instead of `aud`) as the trade-off.
- **Snake_case database columns** via EF Core's naming-convention package, so the C# entity model and the raw SQL (RLS policies, future analytics queries) stay in the same vocabulary rather than fighting a PascalCase/snake_case mismatch everywhere.

- **The anonymization pipeline is the product's actual differentiator, so it got built before anything else on the roadmap** — `RawEntry` → LLM sanitization pass (Anthropic, model chosen for a structured find-and-replace-shaped task rather than open-ended generation) → creator review of a `SanitizedPreview` → approval writes a separate `PublishedEntry` row plus a `SanitizationAudit` (model version, a diff summary, approver, timestamp). Raw and published content stay in physically separate tables, same principle as Sprint 0's RLS design, just applied to content instead of tenant rows.
- **The sanitization prompt does two jobs at once**: strip employer-identifying details (using the creator's own `Experience.CompanyLabel` values as a known-terms blocklist so the model isn't guessing) and screen for prompt-injection-shaped content, since a sprint entry is later retrieved as RAG context for every recruiter who queries that candidate — a malicious instruction hidden in an entry would otherwise be replayed to every future reader. A regex safety net (emails, ticket IDs, internal hostnames) runs after the LLM pass as a deterministic backstop.
- **The sanitization audit trail deliberately doesn't store a raw-vs-sanitized text diff** — only a length delta plus model version/approver/timestamp. Storing the raw text anywhere outside `raw_entries`, even in a non-public audit table, would grow the exact leak surface the pipeline exists to shrink.
- **Synchronous for now, async later**: sanitization runs inline on the API request rather than through a background job queue, since Hangfire isn't wired up yet. The architecture doc's flowchart describes the async version — this is the same steps, just not yet decoupled from the request/response cycle.

- **Home and Experience shipped together, matching the split decided during design**: a recruiter's first-pass scan (Experience) and deep-dive (Sprint Journal) are different jobs, so the two pages stay visually distinct — Experience is a dense, dated timeline; Home is a hook. Built as a `/[slug]` dynamic route so the multi-tenant model reaches all the way to the URL, with a shared layout carrying the persistent nav, the floating Ask AI widget, and the Request Interview CTA across every page in the portfolio.
- **The "no job yet" state got built as a real path, not a fallback.** `currentRoleTitle` is nullable end to end — when null, Home renders "Actively building" instead of a title and simply omits the years-of-experience stat rather than showing "0 years." A second mock fixture (`new-grad-demo`) exists specifically to keep this state visible while building, instead of only ever looking at the fully-staffed demo data.
- **Years of experience is computed, not stored** — derived client-side from the earliest `Employer`-type experience's start date, deliberately excluding PersonalProject/OpenSource/Freelance/Education from that specific stat so it keeps its conventional meaning.
- **Ask AI and Request Interview are real, placed correctly, and honest about not working yet.** Both render in their final positions (Ask AI floating + embedded in the Home hero per the Product Brief; Request Interview next to it) but every interaction explains what's still missing (the embedding pipeline; the interview_requests backend) rather than faking a response — so the UI shape is real ahead of the pipelines that will drive it.
- **Frontend/backend built ahead of the wiring between them.** No API client exists yet — pages read from a mock data module (`lib/mock-portfolio.ts`) shaped like the real `GET /api/portfolio/:slug` response will be, so swapping mock for fetch later shouldn't ripple through the page components.

- **Ask AI is real now, and it's anonymous by design.** `POST /api/portfolio/{slug}/ask` embeds the recruiter's question (OpenAI `text-embedding-3-small`), runs a cosine-similarity search over that candidate's `embeddings` via pgvector, and asks Anthropic to answer using only the retrieved chunks — no login required, matching the MVP roadmap's Phase 1 scope ("anonymous browsing... single-candidate Ask AI"; recruiter accounts become first-class only in Phase 2 billing). A lightweight `ai_query_logs` table backs a simple per-tenant hourly rate cap in the meantime.
- **Embeddings only ever come from `published_entries`, not a separate `Experience`-row path.** The architecture doc describes a polymorphic source_type (published entries and experiences), but as the schema is actually built, an Experience's narrative content only reaches the public layer by first passing through the same raw_entries → sanitize → approve flow as a sprint entry — so `PublishedEntry` is the only real embedding source today. Kept the enum polymorphic anyway so a direct Experience-row path can be added later without a schema change.
- **Two separate model vendors for one "LLM Gateway."** Anthropic doesn't offer an embeddings endpoint, so embeddings come from OpenAI (`text-embedding-3-small`, 1536 dimensions) while generation stays on Anthropic — `ILlmProvider` and the new `IEmbeddingProvider` are split accordingly, following the same named-HttpClient pattern.
- **Chunking is paragraph-based, not section-based**, because entries are stored as a single free-text blob rather than structured Problem/Solution/Technical Design fields — a simplification carried over from how `RawEntry` was originally modeled, noted for revisiting if entries ever gain structured sections.
- **Prompt-injection defense now covers both ends of the pipeline**: write-time (the sanitization pass screens for injection-shaped content before anything is published) and query-time (retrieved chunks are wrapped in tagged, explicitly-untrusted blocks in the RAG prompt, so even content that slipped past the first screen can't hijack the answer given to a recruiter).
- **`published_entries` and the new `embeddings` table needed a second, public-facing RLS policy** — 001's script deliberately only granted the owning tenant's session access and flagged this exact gap in a comment. Ask AI is the anonymous endpoint that finally needed it: Postgres combines multiple permissive policies with OR, so each table now allows "owning tenant's session" OR "portfolio is publicly visible."
- **The LLM Gateway abstraction paid for itself within the same milestone it shipped in.** Getting an Anthropic console API key working hit friction, so generation needed to move to OpenAI — because `ILlmProvider` already existed as an interface with `AnthropicLlmProvider` as its only implementation, this was a config change (`Ai:GenerationProvider`), not a rewrite: added `OpenAiLlmProvider`, extracted the shared system prompts into `LlmSystemPrompts` so both vendors run identical sanitization rules and RAG safety framing, and DI now resolves whichever provider the config points at. Embeddings and generation also got consolidated onto one `OpenAiOptions`/one API key, since there's no reason to ask for two when a single OpenAI key covers both.
- **Flagged, not fixed: table-owner RLS bypass.** In this local setup the app connects as the tables' owning Postgres role, and owners bypass RLS by default unless `FORCE ROW LEVEL SECURITY` is set. The isolation proof test still validates the policy logic itself, but before real traffic this needs a non-owner app role — written down in `sql/002` rather than silently assumed away.
- **A NuGet downgrade error turned into a real "should we upgrade" question, and the obvious-seeming answer was wrong.** Pinning `Pgvector.EntityFrameworkCore` to a version compatible with EF Core 8 fixed the immediate restore error, but the instinct to "just move to .NET 9" turned out to be a bad trade once actually checked: Microsoft extended .NET 9's STS support window to 24 months, which lands its end-of-support on the exact same date as .NET 8's — November 10, 2026. .NET 10, the current LTS, runs to November 2028. Went with .NET 10 instead, which also let the `Pgvector.EntityFrameworkCore` pin come back off (0.3.0 needs a newer Npgsql provider that only exists on EF Core 9+).
- **The post-upgrade CS1705 wasn't a stale-cache problem, even though it looked exactly like one.** After the .NET 10 upgrade, `DevLog.Api` failed with a hard version-mismatch error on `Microsoft.EntityFrameworkCore.Relational` (10.0.4 vs 10.0.8) — a bin/obj clean-and-rebuild didn't fix it, which was the first real signal something deeper was going on. Root cause, found by pulling each package's actual dependency ranges from NuGet: `Microsoft.EntityFrameworkCore` itself doesn't reference `.Relational` at all; only `Npgsql.EntityFrameworkCore.PostgreSQL` does (floor: 10.0.4), and NuGet resolves to the *lowest* satisfying version per project when nothing forces higher. `DevLog.Infrastructure` had nothing forcing higher, so it compiled against `.Relational` 10.0.4, while `DevLog.Api`'s own direct `Microsoft.EntityFrameworkCore.Design` reference required `.Relational` >= 10.0.8 — two projects, two genuinely different resolved versions of the same assembly. Fixed by adding an explicit `Microsoft.EntityFrameworkCore.Relational` 10.0.8 PackageReference to `DevLog.Infrastructure.csproj`, forcing the same version everywhere. Worth remembering: an MSB3277/CS1705 pair that survives a clean rebuild is telling you the conflict is real, not cached — check actual dependency floors before re-cleaning.
- **Request Interview is the last Phase 1 core feature, and it's the first RLS policy in this schema that grants anonymous *write* access, not just anonymous read.** Every prior public-facing policy (002's `public_read` on `published_entries`/`embeddings`) only ever opened up SELECT for the connection with no `app.current_tenant` set. A recruiter submitting an interview request has no login in Phase 1, so `sql/003`'s `public_insert` policy is a `FOR INSERT ... WITH CHECK` gated on the target portfolio's visibility — the INSERT-side mirror of 002's read policy, combined via Postgres's standard "multiple PERMISSIVE policies OR together" behavior with the existing `tenant_isolation` policy that still gives the creator SELECT/UPDATE on their own tenant's rows (for the inbox and accept/decline).
- **No creator inbox UI shipped with this milestone, on purpose.** The MVP roadmap is explicit: "instrument everything, ship no dashboard... query the tables directly for now." `GET /api/interview-requests` plus accept/decline exist so the creator *can* act on requests today, but the actual dashboard surface is a Phase 2 item once there's enough usage data to justify building one. Same shape as Milestone 2, which shipped `EntriesController` and a curl smoke test well before any UI existed for it.
- **The file-write/truncation sandbox bug (documented as fixed in Milestone 4) recurred on two files in this milestone** (`ServiceCollectionExtensions.cs` after a second same-session edit, and the newly-created `RequestInterviewButton.tsx`) — same signature as before: the edit/write tool reported success and Claude's own Read-tool view showed correct content, but the file on disk was truncated mid-line. Caught by a byte-level check (`wc -lc` + `tail` + a null-byte scan) run as a matter of course after every batch of file writes, not just when something looked wrong — and fixed the same way, a bash heredoc rewrite. Worth treating as a standing risk for this sandbox rather than a one-time bug: verify byte-for-byte after any file touched more than once, or any brand-new file with substantial content, before trusting it.
- **Email integration deliberately scoped to one thing: closing the creator-notification gap Milestone 5 left open.** The architecture doc's Section 6 bundles "notify the creator on insert" and recruiter email verification under the same "email" umbrella, but they're different features solving different problems (one is a convenience, the other is an anti-abuse control) — asked which one to build first rather than assuming "email integration" meant both, and scoped this milestone to just the notification.
- **`IEmailProvider`/`PostmarkEmailProvider` is the third vendor-swap-shaped abstraction in this codebase now** (after `ILlmProvider` and `IEmbeddingProvider`), same typed-HttpClient-behind-an-interface pattern each time. The pattern's paid for itself twice already (the Anthropic→OpenAI swap in Milestone 4), which is the whole justification for applying it here too even though there's no concrete SendGrid implementation sitting alongside Postmark yet — unlike the LLM Gateway, there was no forcing function (blocked API key) that required a second implementation to exist yet.
- **The notification send is best-effort by design, not by oversight.** `InterviewRequestService.NotifyCreatorAsync` catches and logs rather than propagates — a recruiter's request is already durably saved in Postgres by the time the email attempt runs, so a Postmark outage, a bad API key, or a creator who hasn't set `NotificationEmail` yet must never turn into a failed submission for the recruiter. This is the same "the write already succeeded, the notification is a convenience" reasoning that would apply to any future Hangfire-based version of this, just enforced with a try/catch instead of a queue for now.
- **`Portfolio` still has no update endpoint**, flagged rather than fixed here — `NotificationEmail` (like every other Portfolio field) currently has to be set directly via SQL/EF, since `PortfolioController` only ever grew a `GET /me`. Worth closing before this needs to work for anyone other than Chika dogfooding it directly against the database.

## Challenges

- **The RLS policy and the EF Core schema disagreed on column casing.** EF Core defaults to PascalCase column names (`TenantId`); the RLS SQL was written assuming Postgres convention (`tenant_id`). First attempt to apply the RLS script failed with `column "tenant_id" does not exist`. Fixed at the root — added `EFCore.NamingConventions` and `UseSnakeCaseNamingConvention()` — rather than patching the SQL to match PascalCase, since every future hand-written SQL snippet would have hit the same mismatch otherwise.
- **The JWT spike caught exactly what it was designed to catch.** The first real Clerk token came back with an `azp` claim of Clerk's own dashboard origin, not the application's — because `window.Clerk.session.getToken()` was run from the Clerk Dashboard page itself rather than the application's hosted Account Portal sign-in page. Once corrected, the token's `azp` still didn't match the assumed `http://localhost:3000` (that assumption was for testing via a real frontend; testing via Clerk's hosted Account Portal produces a different origin) — config adjusted to match what was actually being tested with.
- **`next build` couldn't be verified end-to-end in the build sandbox** — it tried to download the Linux SWC binary and the sandbox has no network access to `registry.npmjs.org`. Not a real bug: the mounted `node_modules` already has the Windows binary (`swc-win32-x64-msvc`) from Chika's own earlier `npm install`, so `npm run build` on his actual machine uses that directly. Verified what the sandbox could: `tsc --noEmit` and `eslint` both came back clean.
- **A real bug, not just a sandbox quirk: rewriting a file to shorter content didn't truncate it.** Five files that got edited more than once in the same session (`[slug]/layout.tsx`, `AskAiForm.tsx`, `AskAiWidget.tsx`, `Hero.tsx`, `AnthropicLlmProvider.cs`) landed on disk either cut off mid-line or padded with leftover null bytes past the intended ending — confirmed at the byte level (`AnthropicLlmProvider.cs` was exactly its old, longer byte-length, with the tail after the new shorter content zero-filled). Root cause: the edit path wasn't truncating the underlying file to the new content's length when the new content was shorter than what it replaced. Fixed by writing the affected files through a different path (a shell heredoc) that truncates correctly, then verifying byte-for-byte and re-running `tsc --noEmit`/`eslint` clean.
- **PowerShell's `curl` is not curl.** It's aliased to `Invoke-WebRequest`, which doesn't accept curl's `-H` flag at all, producing a parameter-binding error that looked unrelated to auth. Fixed by using `curl.exe` explicitly to reach the real binary.
