## Problem

Standard developer portfolios (a CV, a skills list, a GitHub link) show *what* a developer knows but not *how* they work — the exact evidence a recruiter needs to decide whether to book an interview. The idea: a "developer career operating system" where sprint-level case studies and an AI assistant let recruiters query real technical decisions directly, anonymized so no employer confidentiality is at risk.

## Solution

A multi-tenant SaaS (ASP.NET Core + Postgres + Clerk + Next.js) where each developer gets a portfolio with an Experience timeline, a Sprint Journal of case studies, a Learning Lab, and a persistent AI assistant recruiters can query — all sitting on a write-time anonymization pipeline that sanitizes and requires human approval before anything is public.

## Technical design

- **Tenant isolation enforced twice**: application middleware sets tenant context from a verified Clerk JWT claim, and Postgres Row-Level Security independently refuses cross-tenant rows even if application code has a bug — proven with a test that queries deliberately without a `WHERE tenant_id` clause and confirms RLS alone blocks the leak.
- **Raw and sanitized content are physically separate tables**, not a status flag, so there is no code path — buggy or not — that can expose an unsanitized draft.
- **Clerk over Auth0** for authentication, chosen primarily on cost at the expected mostly-free-tier user volume, accepting a less conventional JWT validation pattern (`azp` claim instead of `aud`) as the trade-off.
- **Snake_case database columns** via EF Core's naming-convention package, so the C# entity model and the raw SQL (RLS policies, future analytics queries) stay in the same vocabulary rather than fighting a PascalCase/snake_case mismatch everywhere.

- **The anonymization pipeline is the product's actual differentiator, so it got built before anything else on the roadmap** — `RawEntry` → LLM sanitization pass (Anthropic, model chosen for a structured find-and-replace-shaped task rather than open-ended generation) → creator review of a `SanitizedPreview` → approval writes a separate `PublishedEntry` row plus a `SanitizationAudit` (model version, a diff summary, approver, timestamp). Raw and published content stay in physically separate tables, same principle as Sprint 0's RLS design, just applied to content instead of tenant rows.
- **The sanitization prompt does two jobs at once**: strip employer-identifying details (using the creator's own `Experience.CompanyLabel` values as a known-terms blocklist so the model isn't guessing) and screen for prompt-injection-shaped content, since a sprint entry is later retrieved as RAG context for every recruiter who queries that candidate — a malicious instruction hidden in an entry would otherwise be replayed to every future reader. A regex safety net (emails, ticket IDs, internal hostnames) runs after the LLM pass as a deterministic backstop.
- **The sanitization audit trail deliberately doesn't store a raw-vs-sanitized text diff** — only a length delta plus model version/approver/timestamp. Storing the raw text anywhere outside `raw_entries`, even in a non-public audit table, would grow the exact leak surface the pipeline exists to shrink.
- **Synchronous for now, async later**: sanitization runs inline on the API request rather than through a background job queue, since Hangfire isn't wired up yet. The architecture doc's flowchart describes the async version — this is the same steps, just not yet decoupled from the request/response cycle.

- **Home and Experience shipped together, matching the split decided during design**: a recruiter's first-pass scan (Experience) and deep-dive (Sprint Journal) are different jobs, so the two pages stay visually distinct — Experience is a dense, dated timeline; Home is a hook. Built as a `/[slug]` dynamic route so the multi-tenant model reaches all the way to the URL, with a shared layout carrying the persistent nav, the floating Ask AI widget, and the Request Interview CTA across every page in the portfolio.
- **The "no job yet" state got built as a real path, not a fallback.** `currentRoleTitle` is nullable end to end — when null, Home renders "Actively building" instead of a title and simply omits the years-of-experience stat rather than showing "0 years." A second mock fixture (`new-grad-demo`) exists specifically to keep this state visible while building, instead of only ever looking at the fully-staffed demo data.
- **Years of experience is computed, not stored** — derived client-side from the earliest `Employer`-type experience's start date, deliberately excluding PersonalProject/OpenSource/Freelance/Education from that specific stat so it keeps its conventional meaning.
- **Ask AI and Request Interview are real, placed correctly, and honest about not working yet.** Both render in their final positions (Ask AI floating + embedded in the Home hero per the Product Brief; Request Interview next to it) but every interaction explains what's still missing (the embedding pipeline; the interview_requests backend) rather than faking a response — so the UI shape is real ahead of the pipelines that will drive it.
- **Frontend/backend built ahead of the wiring between them.** No API client exists yet — pages read from a mock data module (`lib/mock-portfolio.ts`) shaped like the real `GET /api/portfolio/:slug` response will be, so swapping mock for fetch later shouldn't ripple through the page components.

- **Ask AI is real now, and it's anonymous by design.** `POST /api/portfolio/{slug}/ask` embeds the recruiter's question (OpenAI `text-embedding-3-small`), runs a cosine-similarity search over that candidate's `embeddings` via pgvector, and asks Anthropic to answer using only the retrieved chunks — no login required, matching the MVP roadmap's Phase 1 scope ("anonymous browsing... single-candidate Ask AI"; recruiter accounts become first-class only in Phase 2 billing). A lightweight `ai_query_logs` table backs a simple per-tenant hourly rate cap in the meantime.
- **Embeddings only ever come from `published_entries`, not a separate `Experience`-row path.** The architecture doc describes a polymorphic source_type (published entries and experiences), but as the schema is actually built, an Experience's narrative content only reaches the public layer by first passing through the same raw_entries → sanitize → approve flow as a sprint entry — so `PublishedEntry` is the only real embedding source today. Kept the enum polymorphic anyway so a direct Experience-row path can be added later without a schema change.
- **Two separate model vendors for one "LLM Gateway."** Anthropic doesn't offer an embeddings endpoint, so embeddings come from OpenAI (`text-embedding-3-small`, 1536 dimensions) while generation stays on Anthropic — `ILlmProvider` and the new `IEmbeddingProvider` are split accordingly, following the same named-HttpClient pattern.
- **Chunking is paragraph-based, not section-based**, because entries are stored as a single free-text blob rather than structured Problem/Solution/Technical Design fields — a simplification carried over from how `RawEntry` was originally modeled, noted for revisiting if entries ever gain structured sections.
- **Prompt-injection defense now covers both ends of the pipeline**: write-time (the sanitization pass screens for injection-shaped content before anything is published) and query-time (retrieved chunks are wrapped in tagged, explicitly-untrusted blocks in the RAG prompt, so even content that slipped past the first screen can't hijack the answer given to a recruiter).
- **`published_entries` and the new `embeddings` table needed a second, public-facing RLS policy** — 001's script deliberately only granted the owning tenant's session access and flagged this exact gap in a comment. Ask AI is the anonymous endpoint that finally needed it: Postgres combines multiple permissive policies with OR, so each table now allows "owning tenant's session" OR "portfolio is publicly visible."
- **The LLM Gateway abstraction paid for itself within the same milestone it shipped in.** Getting an Anthropic console API key working hit friction, so generation needed to move to OpenAI — because `ILlmProvider` already existed as an interface with `AnthropicLlmProvider` as its only implementation, this was a config change (`Ai:GenerationProvider`), not a rewrite: added `OpenAiLlmProvider`, extracted the shared system prompts into `LlmSystemPrompts` so both vendors run identical sanitization rules and RAG safety framing, and DI now resolves whichever provider the config points at. Embeddings and generation also got consolidated onto one `OpenAiOptions`/one API key, since there's no reason to ask for two when a single OpenAI key covers both.
- **Flagged, not fixed: table-owner RLS bypass.** In this local setup the app connects as the tables' owning Postgres role, and owners bypass RLS by default unless `FORCE ROW LEVEL SECURITY` is set. The isolation proof test still validates the policy logic itself, but before real traffic this needs a non-owner app role — written down in `sql/002` rather than silently assumed away.
- **A NuGet downgrade error turned into a real "should we upgrade" question, and the obvious-seeming answer was wrong.** Pinning `Pgvector.EntityFrameworkCore` to a version compatible with EF Core 8 fixed the immediate restore error, but the instinct to "just move to .NET 9" turned out to be a bad trade once actually checked: Microsoft extended .NET 9's STS support window to 24 months, which lands its end-of-support on the exact same date as .NET 8's — November 10, 2026. .NET 10, the current LTS, runs to November 2028. Went with .NET 10 instead, which also let the `Pgvector.EntityFrameworkCore` pin come back off (0.3.0 needs a newer Npgsql provider that only exists on EF Core 9+).
- **The post-upgrade CS1705 wasn't a stale-cache problem, even though it looked exactly like one.** After the .NET 10 upgrade, `DevLog.Api` failed with a hard version-mismatch error on `Microsoft.EntityFrameworkCore.Relational` (10.0.4 vs 10.0.8) — a bin/obj clean-and-rebuild didn't fix it, which was the first real signal something deeper was going on. Root cause, found by pulling each package's actual dependency ranges from NuGet: `Microsoft.EntityFrameworkCore` itself doesn't reference `.Relational` at all; only `Npgsql.EntityFrameworkCore.PostgreSQL` does (floor: 10.0.4), and NuGet resolves to the *lowest* satisfying version per project when nothing forces higher. `DevLog.Infrastructure` had nothing forcing higher, so it compiled against `.Relational` 10.0.4, while `DevLog.Api`'s own direct `Microsoft.EntityFrameworkCore.Design` reference required `.Relational` >= 10.0.8 — two projects, two genuinely different resolved versions of the same assembly. Fixed by adding an explicit `Microsoft.EntityFrameworkCore.Relational` 10.0.8 PackageReference to `DevLog.Infrastructure.csproj`, forcing the same version everywhere. Worth remembering: an MSB3277/CS1705 pair that survives a clean rebuild is telling you the conflict is real, not cached — check actual dependency floors before re-cleaning.
- **Request Interview is the last Phase 1 core feature, and it's the first RLS policy in this schema that grants anonymous *write* access, not just anonymous read.** Every prior public-facing policy (002's `public_read` on `published_entries`/`embeddings`) only ever opened up SELECT for the connection with no `app.current_tenant` set. A recruiter submitting an interview request has no login in Phase 1, so `sql/003`'s `public_insert` policy is a `FOR INSERT ... WITH CHECK` gated on the target portfolio's visibility — the INSERT-side mirror of 002's read policy, combined via Postgres's standard "multiple PERMISSIVE policies OR together" behavior with the existing `tenant_isolation` policy that still gives the creator SELECT/UPDATE on their own tenant's rows (for the inbox and accept/decline).
- **No creator inbox UI shipped with this milestone, on purpose.** The MVP roadmap is explicit: "instrument everything, ship no dashboard... query the tables directly for now." `GET /api/interview-requests` plus accept/decline exist so the creator *can* act on requests today, but the actual dashboard surface is a Phase 2 item once there's enough usage data to justify building one. Same shape as Milestone 2, which shipped `EntriesController` and a curl smoke test well before any UI existed for it.
- **The file-write/truncation sandbox bug (documented as fixed in Milestone 4) recurred on two files in this milestone** (`ServiceCollectionExtensions.cs` after a second same-session edit, and the newly-created `RequestInterviewButton.tsx`) — same signature as before: the edit/write tool reported success and Claude's own Read-tool view showed correct content, but the file on disk was truncated mid-line. Caught by a byte-level check (`wc -lc` + `tail` + a null-byte scan) run as a matter of course after every batch of file writes, not just when something looked wrong — and fixed the same way, a bash heredoc rewrite. Worth treating as a standing risk for this sandbox rather than a one-time bug: verify byte-for-byte after any file touched more than once, or any brand-new file with substantial content, before trusting it.
- **Email integration deliberately scoped to one thing: closing the creator-notification gap Milestone 5 left open.** The architecture doc's Section 6 bundles "notify the creator on insert" and recruiter email verification under the same "email" umbrella, but they're different features solving different problems (one is a convenience, the other is an anti-abuse control) — asked which one to build first rather than assuming "email integration" meant both, and scoped this milestone to just the notification.
- **`IEmailProvider`/`PostmarkEmailProvider` is the third vendor-swap-shaped abstraction in this codebase now** (after `ILlmProvider` and `IEmbeddingProvider`), same typed-HttpClient-behind-an-interface pattern each time. The pattern's paid for itself twice already (the Anthropic→OpenAI swap in Milestone 4), which is the whole justification for applying it here too even though there's no concrete SendGrid implementation sitting alongside Postmark yet — unlike the LLM Gateway, there was no forcing function (blocked API key) that required a second implementation to exist yet.
- **The notification send is best-effort by design, not by oversight.** `InterviewRequestService.NotifyCreatorAsync` catches and logs rather than propagates — a recruiter's request is already durably saved in Postgres by the time the email attempt runs, so a Postmark outage, a bad API key, or a creator who hasn't set `NotificationEmail` yet must never turn into a failed submission for the recruiter. This is the same "the write already succeeded, the notification is a convenience" reasoning that would apply to any future Hangfire-based version of this, just enforced with a try/catch instead of a queue for now.
- **`Portfolio` still has no update endpoint**, flagged rather than fixed here — `NotificationEmail` (like every other Portfolio field) currently has to be set directly via SQL/EF, since `PortfolioController` only ever grew a `GET /me`. Worth closing before this needs to work for anyone other than Chika dogfooding it directly against the database.
- **"Build onboarding" turned out to mean "make every authenticated endpoint work for the first time," not "add a signup form."** Tracing `TenantResolutionMiddleware` to design the fix surfaced that it read a custom `tenant_id` JWT claim nothing ever configured Clerk to issue — meaning `EntriesController`, `CreatorInterviewRequestsController`, and `PortfolioController` had never actually been reachable by a real Clerk-issued token, only by directly hand-set `CurrentTenantAccessor` state in tests or by the manual SQL rows used for every smoke test so far. The gap wasn't "no signup step," it was "no tenant_id claim ever gets minted," which is a materially bigger and more foundational bug than it first looked like from the outside.
- **Auto-provision-on-first-request over a Clerk webhook, chosen explicitly rather than defaulted to.** A webhook (`user.created` → create Tenant/Portfolio → push a `tenant_id` claim into Clerk's user metadata → Clerk JWT template picks it up) is the more conventional pattern, but needs webhook signature verification, a publicly reachable endpoint even for local dev, and a Clerk dashboard JWT template edit. Asked which approach before building either, since this was a genuine fork the architecture doc never actually resolved (it describes steady-state auth once a `tenant_id` claim exists, never how the claim is minted the first time) — chose the simpler synchronous option, consistent with every other "defer the queue/infra" decision made so far in this build.
- **Found a second latent bug while designing the first one's fix: `portfolios` had zero RLS policies across `sql/001-003`.** `GetMyPortfolio`'s comment claimed RLS enforced scope with no WHERE clause, same pattern as `EntriesController` — but that pattern only holds for tables where a caller can never see another tenant's row *at all*. `portfolios` needs a `public_read` policy (Ask AI and Request Interview both look up a portfolio by slug anonymously), which means an authenticated caller can legitimately see rows beyond their own — so "no WHERE clause" stopped being safe the moment RLS got added properly. Fixed by both adding the missing policy and adding the explicit tenant filter `GetMyPortfolio` needed regardless.
- **Deliberately did NOT add RLS to `tenants` in the same pass, unlike `portfolios`.** Two reasons, not an oversight: nothing on that row is actually sensitive (Clerk user id, a public slug, a plan tier — the real leak surface is raw_entries/published_entries/embeddings, already covered), and `TenantProvisioningService`'s own lookup runs *before* `app.current_tenant` is known for that request — RLS-protecting `tenants` would make the provisioning service unable to find a returning user's own row on their second-and-later requests, a chicken-and-egg problem with no clean resolution short of a service-role connection bypass.
- **`Tenant.UserId` was typed `Guid` since Sprint 0 and nobody had actually tried to put a real Clerk user id in it until now** — Clerk ids are strings shaped like `user_2abc...`, not GUIDs, so the field could never have held a real value. Caught only because building real provisioning required actually populating it with `sub`, not from a code review pass. Changed to `string` with a unique index (also closes a race: two near-simultaneous first requests from the same brand-new user now resolve to one row via a catch-and-requery on the unique-constraint violation, not two).
- **The "needs FORCE ROW LEVEL SECURITY" note carried in every RLS script since 001 was aiming at the wrong lever, and the mistake stayed invisible for four milestones.** Chika left the choice of what to fix next entirely up to me; picked the table-owner RLS bypass over stored XSS or recruiter email verification specifically because it's not additive — it undermines a guarantee (RLS enforces tenant isolation) every other milestone has been implicitly relying on. Checking the actual mechanism before implementing the "obvious" fix (FORCE ROW LEVEL SECURITY on the owner) turned up that `docker-compose.yml`'s `POSTGRES_USER: devlog` creates a genuine Postgres **superuser**, and Postgres unconditionally disables row security for superusers — FORCE ROW LEVEL SECURITY only affects a non-superuser owner choosing to bind itself to its own policies, and does nothing for an actual superuser. The correct fix isn't "force RLS on the owner," it's "stop connecting as a superuser at all." Worth remembering generally: a security note repeated unchanged across four consecutive milestones is worth re-deriving from the actual mechanism before implementing, not just executing as written — the note itself can be the thing that's subtly wrong.
- **This also means `TenantIsolationTests` — the Sprint 0 exit criterion, "don't move on until this passes" — never actually tested what it claimed to, from Sprint 0 through Milestone 7.** It connected as `devlog` (the superuser) the entire time, so every prior green run could only have proven the RLS policy *SQL* was internally consistent with the test's expectations, not that Postgres was actually blocking anything for the role real traffic uses — superusers bypass RLS regardless of what the policies say. Repointed the test at the new restricted `devlog_app` role so it can actually fail the way it's supposed to. This is worth sitting with: a load-bearing "proof" test having tested nothing real for the majority of the project's history, discovered only because implementing an adjacent fix required understanding the mechanism precisely enough to notice.
- **Fixing that surfaced a second, independent bug in the test's own seed step**, also dormant for the same reason: `NoTenantContext_Sees_Nothing` seeded a row tagged with `tenantId` while `app.current_tenant` was set to a *different*, unrelated random guid on that connection. Under real RLS enforcement, that mismatch should fail `raw_entries`' `tenant_isolation` policy's implicit `WITH CHECK` on insert — but since the seed always ran as the superuser, the mismatch was never actually checked. Fixed by seeding with a context whose tenant matches the row.
- **Two connection strings now exist on purpose, not by accident**: `DevLogDb` (the `devlog` owner role, DDL rights, used only by the new `DevLogDbContextFactory` for `dotnet ef` tooling) and `DevLogDbRuntime` (the new restricted `devlog_app` role, used by the actual running app via `ServiceCollectionExtensions`). `IDesignTimeDbContextFactory<T>` is the mechanism EF Core provides specifically for this split — migrations need elevated rights the running app should never have.
- **"Fix output sanitization on rendered entries" turned into "build the Sprint Journal page," because there was nothing to sanitize yet.** Checked the actual frontend state before writing any code: no `/journal` route, no rendering component, no markdown library installed — the security item was written assuming a renderer already existed to harden. Asked whether to scope up to the real page or just ship the safety infrastructure inert; chose the real page, both because it directly serves Chika's "make the pages functional" goal and because a sanitization fix with nothing rendering through it isn't actually verifiable.
- **No title field existed anywhere in this schema — not on `RawEntry`, not on `PublishedEntry`, not even in the architecture doc's own ERD.** Entries were designed from the start as a single free-text blob (the same design choice `TextChunker`'s paragraph-based chunking already noted). A Sprint Journal listing page needs something to show before a reader opens the full entry, so this got added rather than worked around with a truncated content preview — a real title beats a guessed-at excerpt.
- **`PublishedEntry.SourceEntryType` is a denormalized copy of `RawEntry.EntryType`, not a join, and that's load-bearing, not a shortcut.** `raw_entries` has zero RLS grant for the anon/public role by design (Section 1's "critical isolation detail") — an anonymous Sprint Journal read can never join through to it to filter by type, full stop. Copying the value once at publish time (`SanitizationPipelineService.ApproveAsync`) is what makes the public listing endpoint able to show only `SprintEntry`-sourced rows without touching the locked-down table at all.
- **The actual stored-XSS fix is `react-markdown` never calling `dangerouslySetInnerHTML`, not `rehype-sanitize` — but both got used anyway, deliberately, not redundantly.** `react-markdown` parses markdown into real React elements; without the `rehype-raw` plugin (never imported here), a literal `<script>` tag in entry content renders as inert text automatically, no sanitizer needed for that vector. `rehype-sanitize`'s allowlist pass covers what that alone doesn't: `javascript:` URIs in markdown's own `[text](url)` link syntax, and any dangerous node a future plugin might introduce. Two independent mechanisms stacked, not one relied on twice.
- **Styled the markdown output with an explicit `components` map instead of installing `@tailwindcss/typography` for `prose` classes.** The plugin isn't used anywhere else in this project, and this would have been the only place that needed it — matching the existing all-explicit-utility-classes convention (every other component in this codebase styles this way) was worth more than the convenience of one shorthand class, for one component.
- **ESLint timed out in the sandbox on this milestone's files** (even a single small file exceeded 40s, likely `eslint-config-next`'s type-aware linting building a full TS program on first run) — `tsc --noEmit` came back completely clean across everything instead and was treated as the stronger available signal. Flagged for Chika to run ESLint locally as the real first check, same pattern as `next build`'s existing sandbox caveat.
- **Recruiter email verification is orthogonal to `Status`, not a new state folded into it.** `EmailVerified` answers "is this request real"; `Status` (Pending/Accepted/Declined) answers "what did the creator decide" — kept as two independent fields rather than adding an `AwaitingVerification` status, since a verified-but-undecided request and an unverified one both need to render as "Pending" for any future creator UI, and conflating them would have made that distinction unrecoverable later.
- **The verification link building surfaced its own small design gap, caught before it shipped rather than after.** `InterviewRequestService.SendVerificationEmailAsync`'s URL originally carried only `requestId`/`token`, but the backend `Verify` route is `POST /api/portfolio/{slug}/interview-requests/{id}/verify` — `slug` as a path segment. The lookup itself never needed `slug` (the id+token pair is already globally unique and self-authenticating), but the frontend confirmation page calling back into that route does. Fixed by threading `slug` (already in scope in `CreateAsync`, via `portfolio.Tenant!.Slug`) through into the emailed URL as a query param, alongside `requestId`/`token`.
- **`GET /api/interview-requests`'s new `WHERE EmailVerified` filter is the actual anti-abuse control, not a cosmetic one.** A fabricated or mistyped recruiter email now never appears in the creator's inbox at all — not temporarily, not until some expiry job runs — because it can never complete the verification step. This is the difference between Milestone 6 (which notified the creator on unverified submissions) and this milestone.
- **"Ship it so I can use it myself" turned into a full audit of what "feature-complete" actually meant, and the honest answer was: half a product.** Every prior milestone built the recruiter/viewer half correctly, but nothing ever built the creator half's UI — writing entries, editing a profile, managing requests were curl-only by design (the roadmap's "ship no dashboard" call), which was the right call for an external recruiter demo and the wrong one for daily personal use. Surfaced by actually checking, not assuming: grepped the frontend for a settings/dashboard/composer route and found none, then checked whether the public pages were even real and found they were still 100% Milestone 3 mock data.
- **`experiences` had zero RLS policy across `sql/001-005` — worse than the portfolios gap from Milestone 7, not the same shape.** Portfolios was "missing public_read but had tenant_isolation." Experiences had *nothing enabled at all*, meaning any connection with `SELECT`/`INSERT` grants (including the restricted `devlog_app` role from Milestone 8) could read or write any tenant's rows — invisible only because nothing had ever queried the table through the app before this milestone needed to. Fixed via `sql/006`, same tenant_isolation + public_read shape as everything else, with the public_read policy needing a cross-table `EXISTS` against `portfolios.visibility` since experiences has no visibility column of its own (same pattern as 003's `public_insert` on interview_requests).
- **Enums were never actually serializing as strings, and this had been silently true since Milestone 2.** Nothing in `Program.cs` ever registered a `JsonStringEnumConverter`, so System.Text.Json's real default (serialize as the underlying int) had been in effect the whole time — meaning every prior curl example in GETTING-STARTED.md that sent an enum as a JSON string would actually have failed to deserialize, and every prior response that included one would have returned a bare number instead of "Pending"/"Unlisted"/etc. Caught only because this milestone's dashboard reads those fields back and does string-keyed lookups against them (`STATUS_LABEL[entry.status]` and similar) — the first code in this project to actually consume an enum value from a live API response rather than just set one. Fixed once, globally, in `Program.cs` rather than per-DTO.
- **`Portfolio.DisplayName`/`PositioningLine`/`PhotoUrl` and `Experience.Title` didn't exist on the backend at all — the frontend's `PortfolioData`/`ExperienceEntry` types had always been richer than the actual schema.** `Hero.tsx` has referenced `portfolio.displayName` since Milestone 3; nothing on `Portfolio` ever carried it because the mock fixture papered over the gap. Not noticed until building the real `GET /api/portfolio/{slug}` endpoint required actually populating those fields from something.
- **The Clerk frontend SDK genuinely never existed until this milestone — not "misconfigured," entirely absent.** `@clerk/nextjs` wasn't in `package.json`, no `ClerkProvider`, no middleware. Every backend Clerk JWT validation built since Sprint 0 had only ever been exercised by a manually-pasted bearer token via curl. This milestone is the first time a real browser session actually signs a user in and the frontend mints its own token to call the API with — `useApi()`'s `getToken()` call is new code, not a wire-up of something that already worked.
- **After fixing the portfolio cycle, audited every controller action for the same pattern and added a global safety net, not just a point fix.** Grepped every `Ok(`/`CreatedAtAction`/`Created` return across all seven controllers — everything else already went through a `ToDto`/`.Select()` shape (confirmed, not assumed). The underlying cause is structural, though: `Tenant<->Portfolio`, `Tenant<->Subscription`, `RawEntry<->PublishedEntry`, and `PublishedEntry<->SanitizationAudit` are all genuinely bidirectional EF navigations, and EF's change-tracker fixup wires up matching entities across *anything* tracked in the same request-scoped `DbContext`, not just what a given query `.Include()`d — so a future action returning a raw entity can cycle for reasons invisible to whoever wrote that action, exactly like `UpdateMyPortfolio` did. Added `ReferenceHandler.IgnoreCycles` globally in `Program.cs` as defense in depth: if this exact mistake recurs, it degrades to a truncated response instead of a 500, the same "shape it deliberately, but don't rely on that alone" posture as the CSP header and the enum-string fix.
- **A fourth bug, found via `PUT /api/portfolio/me`: `UpdateMyPortfolio` still returned the raw `Portfolio` entity, the exact thing `GetMyPortfolio` was already fixed to avoid.** `System.Text.Json` threw "a possible object cycle was detected" on `Tenant.Portfolio.Tenant.Portfolio...`. Root cause is EF Core's change-tracker fixup, not the query itself: `UpdateMyPortfolio`'s query never `.Include()`d `Tenant`, but `TenantResolutionMiddleware` had already loaded and tracked that tenant's row earlier in the same request (same scoped `DbContext`), and EF wires up matching navigation properties across anything tracked in the same context — not just what a given query explicitly included. The fix applied to `GetMyPortfolio` (shape a DTO, never return the entity) got missed on the sibling action when it shipped. Fixed by extracting a shared `ToMyPortfolioDto` used by both, and added `.Include(p => p.Tenant)` to `UpdateMyPortfolio`'s query too so Slug is reliably available rather than depending on incidental fixup. Checked every other controller for the same raw-entity-return pattern (`SprintJournalController` already projected with `.Select()`, everything else already shaped) — this was the only other occurrence.
- **A third bug, one layer deeper still: auto-provisioning's own INSERT violated the RLS policy it was trying to satisfy.** `TenantProvisioningService.GetOrCreateTenantAsync` creates a brand-new `Tenant` and its placeholder `Portfolio` in one `SaveChangesAsync` — but `TenantConnectionInterceptor` only sets `app.current_tenant` when `ICurrentTenantAccessor.TenantId` is already non-null, and nothing set it until `TenantResolutionMiddleware` read this method's *return value*, after the save already ran. So the Portfolio insert executed with no tenant context at all, and `portfolios`' `tenant_isolation` policy (no explicit `WITH CHECK`, falls back to its `USING` expression) correctly refused a row it couldn't evaluate `tenant_id = NULL` as true for. `tenants` itself was never affected — deliberately has no RLS — which is exactly why the Tenant half of the same save always succeeded while the Portfolio half never could. Fixed by injecting `ICurrentTenantAccessor` into the service and setting `accessor.TenantId = tenantId` for the *new* tenant right before `SaveChangesAsync`, so the interceptor has something to set the GUC from when it opens the connection for that flush. Three layered bugs (azp mismatch, claim-mapping, this one) all had to be peeled back in sequence before a real signed-in user could complete first-time provisioning even once — every prior "smoke test" of this path used a hand-inserted or manually-pasted-token shortcut that skipped straight past all three.
- **After fixing the `azp` mismatch, authentication started succeeding but every dashboard call still 401'd — a second, unrelated bug underneath the first.** `TenantResolutionMiddleware`'s `context.User?.FindFirst("sub")` came back null even with a valid, correctly-issued token, because `System.IdentityModel.Tokens.Jwt` silently remaps short claim names ("sub" → the legacy WS-Federation `.../nameidentifier` URI) when building the `ClaimsPrincipal`, unless `JwtBearerOptions.MapInboundClaims = false` is set — which nothing here ever set. `azp` wasn't affected because it isn't one of the claims in that legacy remap table, which is exactly why the first fix got partway and no further. Diagnosed by having Chika decode his actual token and confirm `azp`/`iss` were both already correct, which ruled out the JWT validation itself and pointed at something downstream — the response body's own "No tenant context resolved from the current token." then named the exact failure point. This is the first time a real Clerk-issued token from the actual running app (not a manually-pasted curl token) ever reached this code path successfully authenticated, which is why it took until Milestone 11 to surface.
- **Milestone 9's hand-maintained CSP header broke Clerk outright, for the same root reason as the SignedIn/SignedOut mistake: written before Clerk existed in this app.** `next.config.ts`'s `script-src 'self' 'unsafe-inline'` had no `'unsafe-eval'` (Next.js dev mode needs it) and no allowance for Clerk's FAPI host, Cloudflare's bot-protection host, or Clerk's abuse/fraud-protection hosts — so both React's dev-mode eval() and Clerk's own JS failed to load, with the browser reporting a generic "Failed to load Clerk JS" rather than naming the CSP block. Fixed by moving CSP ownership into `clerkMiddleware({ contentSecurityPolicy: { directives: {...} } })` in `middleware.ts` (confirmed available and recommended for @clerk/nextjs >=6.14 via Clerk's own docs) instead of hand-maintaining the origin list — `next.config.ts` no longer sets the header at all. `directives` merges our own two additions (the .NET API's connect-src, and a broader img-src for arbitrary creator-supplied photo/CV URLs) on top of Clerk's own default set, so Clerk's required origins can't silently drift out of date the way the hand-written version already had.
- **`SignedIn`/`SignedOut` don't exist in the installed `@clerk/nextjs` (7.6.1) — Clerk replaced them with a unified `Show` component.** Written from memory of Clerk's older API before the package could actually be installed in the sandbox; the moment it installed for real (on Chika's machine) and the app ran, Turbopack's RSC bundler reported the missing exports precisely. Confirmed the real API by requiring the installed package directly (`Object.keys(require('@clerk/nextjs'))`) and reading `Show`'s actual source rather than guessing — it takes `when="signed-in" | "signed-out" | <permission check>"` plus `fallback`. Fixed in `page.tsx`; worth checking for the same pattern anywhere else `SignedIn`/`SignedOut` might get reached for.
- **A second sandbox install failure, different shape from Milestone 9's.** `npm install @clerk/nextjs` hit `ENOTEMPTY` on `@img/sharp-libvips-linux-x64` — an unrelated optional dependency's stale temp-rename directory left over from a much earlier session (dated 11 days prior in the sandbox's own file listing), with one file inside permission-denied on delete (consistent with something on the real machine still holding it open). Unlike Milestone 9's react-markdown install (which completed despite a timeout), this one never completed at all across several retry strategies (`--omit=optional`, `--ignore-scripts`, deleting the stale dir directly). Same fallback as before: hand-edit `package.json`, flag it explicitly, `tsc --noEmit` confirms everything else is clean.
- **A fifth tenant-context bug, found post-launch: `set_config`'s NULL-reset path doesn't return Postgres to a truly "unset" state once a custom GUC has been touched.** Milestone 11's `TenantConnectionInterceptor` only ever called `set_config` when there was a real tenant (skipping entirely for anonymous requests) — which left stale tenant ids on reused pooled connections (`NpgsqlDataSource` is registered as a singleton, so physical connections *do* get handed across unrelated requests), a real isolation gap. The first fix attempt — always call `set_config`, passing SQL `NULL` to "clear" it for anonymous requests — looked correct and matches how `RESET` is normally described, but Postgres custom GUCs don't work that way: the *first* `set_config` call on a session creates a placeholder variable, and once created, resetting it via a NULL value sets it to an **empty string**, not back to "never existed." `current_setting(name, missing_ok=true)` only returns true `NULL` if the GUC was never referenced at all in that session — so any connection that had *ever* carried a real tenant id started returning `""` for every later anonymous reuse, which every RLS policy's `::uuid` cast then choked on (`22P02: invalid input syntax for type uuid: ""`). Root-caused by Chika directly: ruled out a role- or database-level `ALTER ... SET` default first (`pg_roles.rolconfig` and `pg_db_role_setting` both came back empty), which by elimination pointed at the interceptor's own reset logic. Fixed by sending `Guid.Empty` instead of `NULL` for "no tenant" — always a syntactically valid uuid, never colliding with a real tenant id (`TenantProvisioningService` mints ids via `Guid.NewGuid()`), so the RLS cast always succeeds and correctly falls through to any `public_read` policy that exists, or matches zero rows where none does.
- **Milestone 12 closed the two Phase 1 gaps the roadmap review had deliberately deferred, once the premise for deferring them changed.** `portfolio_view_events` and `Subscription.SanitizationQuota` enforcement were both flagged as "cheap now, expensive to retrofit once real tenant data exists" per Section 9 — deferred while usage was personal-only, revisited the moment the plan became "onboard other developers soon." `portfolio_view_events` is a new internal-only table (no public_read policy, same shape as `ai_query_logs`), logged in `PortfolioController.GetPublicPortfolio` on every successful public load — best-effort, wrapped in a try/catch so a logging failure can never break an actual page view. The sanitization rate cap turned out to need two independent checks, not one: a short-window abuse cap (`sanitization_run_logs`, hourly count, mirrors `AskAiService`'s existing hourly-cap shape) and the pre-existing `Subscription.SanitizationQuota` field, which had carried a doc comment since early in the build claiming it existed "specifically so a per-tenant rate cap can be enforced" — but nothing had ever counted against it. Both now do, off the same `sanitization_run_logs` table (a rolling-hour count for the abuse cap, a calendar-month count for the quota), logged once per real `SanitizeAsync` call rather than once per approved entry, since a creator re-running sanitize on a draft is a real LLM cost each time whether or not it's ever approved.
- **Deliberately scoped Milestone 12 to just the two deferred gaps, not the full Phase 2 list, despite "implement everything" being the actual request.** Phase 2 as roadmapped is realistically five-plus milestones (onboarding automation, paused visibility, Discover, creator analytics, Learning Lab, billing) — asked two genuine forks before sequencing rather than assuming: whether billing should block onboarding (deferred — free for now, same reasoning the roadmap already used once), and whether to close the two deferred gaps now given the premise shift (yes). Also deliberately dropped the `discipline`/multi-role expansion from the sequence — it exists to onboard non-developer roles, and the stated goal is onboarding other *developers*, so it doesn't serve the goal as stated.
- **Chika's own testing caught a real bug in Milestone 12's own logging: `portfolio_view_events` stayed empty despite repeated page loads, and it turned out to be a rediscovery of a lesson this build had already learned once.** `sql/007` gave `portfolio_view_events` only a bare `tenant_isolation` policy with no explicit `WITH CHECK` — the same shape that caused `TenantProvisioningService`'s RLS chicken-and-egg bug earlier in this build (a policy with no explicit `WITH CHECK` falls back to using its `USING` expression for INSERT too). `GetPublicPortfolio` is anonymous, so that connection never carries a real `app.current_tenant`, meaning every insert attempt evaluated `tenant_id = current_setting(...)::uuid` against a value that could never match, and Postgres silently rejected the row — silently because the `catch { }` wrapping the insert logged nothing at all. Checking for the same shape elsewhere (rather than just patching this one instance) found `ai_query_logs` had carried the identical gap since Milestone 4, undiscovered until now: it only ever got `tenant_isolation` in `sql/002`, never a `public_insert` policy, and `AskAiService`'s insert has no try/catch at all — meaning every Ask AI question could have been throwing a 500 instead of returning an answer, silently, since the feature first shipped. Fixed via `sql/008` (adds `public_insert` to both tables, same `EXISTS`-against-`portfolios.visibility` shape as `interview_requests`' existing `public_insert` policy from `sql/003`) plus two code changes: `PortfolioController`'s swallow now logs via `ILogger` instead of going silent, and `AskAiService`'s previously-unguarded insert is now wrapped in the same best-effort try/catch, so a rate-limit-log failure can never cost a recruiter their already-generated answer. Worth remembering generally: an RLS policy with no explicit `WITH CHECK` on a table any anonymous/cross-tenant code path writes to is a recurring shape of bug in this schema, not a one-off — worth grepping for the pattern (`tenant_isolation`-only policy + an anonymous write path) whenever a new log/analytics table is added.
- **Chika caught Ask AI giving a wrong-feeling answer — "any C# experience?" returned "I don't see specific evidence" — which traced back to a real architecture gap flagged and deliberately deferred all the way back in Milestone 4.** `EmbeddingPipelineService` only ever embedded `PublishedEntry.SanitizedContent`; `Experience` rows (where a candidate's actual tech stack lives, in the structured `Technologies` list) had no path into the `embeddings` table at all — not even the indirect one Milestone 4's own doc comment assumed existed ("Experience content reaches RAG via raw_entries -> sanitize -> approve"), because Milestone 11 built `ExperienceController` as direct CRUD straight onto the `experiences` table, bypassing that assumed path entirely and nobody revisited the comment. First confirmed the immediate case wasn't just "no data" (Chika had zero published Sprint Journal entries yet, so the embeddings table was genuinely empty) before concluding the deeper gap also applied — asked directly rather than assuming. Fixed by adding `EmbeddingSourceType.Experience` (a pure string-column addition, no migration needed) and `EmbeddingPipelineService.EmbedExperienceAsync`, called directly from `ExperienceController`'s Create/Update/Delete. Deliberately skips the sanitize pipeline entirely, unlike published entries — `Experience.CompanyLabel` is free text the creator types themselves, already documented as "never a foreign key to a real employer record," so there's nothing here an LLM sanitization pass would need to catch. Flattened each Experience row into natural-language text (title, company, period, technologies, key achievement) rather than a label:value dump, so it chunks and retrieves the way the rest of the RAG prompt content already does. `AskAiService`'s retrieval query needed no changes — it already searches `embeddings` with no `SourceType` filter, so Experience chunks are included automatically once they exist. Existing Experience rows need a one-time backfill: editing and re-saving each one via the dashboard now triggers embedding, same as it always should have.
- **Milestone 13 is the first Phase 2 feature: GitHub import, the first slice of guided onboarding.** Two genuine forks decided via AskUserQuestion before building, not assumed: public-username lookup over full OAuth (no token storage, works for anyone, at the cost of GitHub's 60-req/hour unauthenticated rate limit — a deliberate, named trade-off, not an oversight), and resume upload deliberately deferred to its own milestone (13b, scheduled immediately next) rather than bundled in, since it needs file-upload handling and its own security pass the roadmap already calls out separately ("resume upload hardening"). Extended `ILlmProvider` with a fourth method, `SuggestOnboardingContentAsync`, following the exact same shared-prompt-in-`LlmSystemPrompts` pattern as sanitization and RAG — one prompt, both vendors, so switching `Ai:GenerationProvider` can never change onboarding behavior any more than it can change sanitization rules. Unlike the other two methods, this one asks for structured JSON output (one Experience suggestion per GitHub repo, plus a single AI-drafted Sprint Journal entry from whichever repo has the richest README) rather than free text, since the caller needs to map the result onto real form fields, not just display prose. The service that calls it (`OnboardingImportService`) is deliberately read-only — it persists nothing. `POST /api/onboarding/github-import` returns suggestions; saving one is just the frontend calling the *same* `POST /api/experiences`/`POST /api/entries` endpoints a creator would hit typing by hand, reviewed and explicitly accepted first. This is what keeps the feature from needing its own copy of any safety rule those endpoints already enforce — a drafted Sprint Journal entry still lands as an ordinary `Draft` and goes through the real sanitize → approve pipeline, satisfying the roadmap's explicit "nothing bypasses the sanitize-and-approve pipeline" requirement without any special-casing.
- **Suggested Experience dates come from GitHub's own repo metadata (`created_at`/`pushed_at`), not the LLM.** Asking a model to guess dates when exact ones already exist in the source data would just be a worse version of information already available — and one less thing for the extraction prompt to hallucinate. `EndDate` defaults to the repo's last-pushed date as a reasonable draft ("last time I was actively working on this"), not a claim the project is finished — the creator can blank it to "present" before saving either way.
- **Milestone 13b's resume-suggestion prompt has to do its own anonymization, because there's no downstream pass that will.** Every other place free-text employer data touches this app either never leaves the creator's own typing (`Experience.CompanyLabel`, "never a foreign key to a real employer record" by design) or passes through `SanitizationPipelineService` before anything public sees it (Sprint Journal entries). A resume is neither — it's raw third-party text the LLM reads and must transform in the *same* pass it extracts from, since nothing catches a leaked real employer name afterward. `BuildResumeSuggestionSystemPrompt` carries an explicit CRITICAL rule on `companyLabel` for exactly this reason, distinct from `BuildOnboardingSuggestionSystemPrompt` (GitHub's prompt needs no such rule — READMEs are already public).
- **Chose PdfPig over sending the raw PDF straight to the LLM's multimodal API, a real trade-off, not a default.** Both `AnthropicLlmProvider` and `OpenAiLlmProvider`'s current request DTOs are text-only — extending them to carry a file/document content block would touch the same shared code path every other prompt in this app depends on, and doing that without being able to compile-test the change in this sandbox was judged too risky for what it'd save. `UglyToad.PdfPig` (MIT-licensed, pure managed C#, no native dependency to worry about across platforms) keeps resume import on the exact same "extract text, feed it to a text-only prompt" shape GitHub import's README extraction already proved out. Trade-off named on purpose: scanned/image-only resumes with no embedded text layer produce no suggestions — the file still gets stored and hosted as the CV download either way, so the upload isn't wasted, but extraction silently can't help in that case.
- **The resume file gets stored before the rate-limit check or the LLM call, not after — a deliberate ordering, not an oversight.** A creator choosing to upload and host a resume is a real action that should succeed independently of whatever the AI-suggestion half decides to do with it; gating storage behind "did the extraction succeed" would mean a scanned PDF, a rate-limited request, or a flaky LLM call could all silently prevent someone from setting their CV download link, which has nothing to do with any of those failure modes. `SuggestFromResumeAsync` always calls `IFileStorageProvider.SaveAsync` and updates `Portfolio.CvFileUrl` first, then layers the rate cap and extraction on top.
- **`IFileStorageProvider` is the fourth vendor-swap-shaped abstraction in this codebase, same reasoning as `ILlmProvider`/`IEmbeddingProvider`/`IEmailProvider` before it.** `LocalDiskFileStorageProvider` is the only implementation, matching this build's actual "local only, for now" hosting decision — but the interface exists so a future Azure Blob Storage implementation slots in behind `SaveAsync`'s one method without touching `OnboardingImportService` or anything else that calls it, the same swap-without-rewrite story every other provider in this codebase already tells.
- **File upload got three independent validation layers before it reaches any real processing, deliberately more paranoid than any other endpoint in this codebase.** `OnboardingController.ResumeImport` checks the extension (`.pdf`), the size (10MB via both `[RequestSizeLimit]` and an explicit length check), and the actual first bytes against the real PDF magic header (`%PDF-`) — the last one specifically because a browser's reported `Content-Type` on a file input can't be trusted and a renamed `.txt` would otherwise sail past an extension-only check straight into `PdfTextExtractor`.
- **`UglyToad.PdfPig` was the wrong package ID — a real NU1103 restore failure on Chika's machine caught it, not a code review.** The project is still namespaced `UglyToad.PdfPig` in code (confirmed via the maintainers' own README), but the actively maintained package publishes to nuget.org under the bare ID `PdfPig`, not `UglyToad.PdfPig` — that second package ID exists too, but it's a different, separately-owned listing (owner `grinay`, last published 2023, non-standard version strings like `1.7.0-custom-5`), not the project the original comment described. Verified directly against nuget.org and the GitHub repo's own issue tracker before fixing, rather than guessing a second version number — worth remembering generally: a "package not found at this version" NU1103 is worth checking the actual package ID against the project's own docs before assuming it's just a stale version pin.
- **Milestone 14 (paused visibility) turned out to already be fully built — checked the running code before starting, rather than trusting the roadmap's "⬜ Not started" tag.** `Paused` has been enforceable since Sprint 0 (it's always been in the `PortfolioVisibility` enum), `sql/004`'s RLS `public_read` policy already excludes it at the database layer, all four anonymous read paths (`PortfolioController.GetPublicPortfolio`, `AskAiService`, `InterviewRequestService.CreateAsync`, `SprintJournalController`) already re-check it explicitly, and Milestone 11's dashboard already shipped a working `<select>` control for it. Roadmap corrected in place rather than re-implementing something that already worked — the same "verify against actual code state before proposing work" discipline this build has used since Milestone 7's roadmap review, just applied to conclude nothing needed to change instead of finding a gap.

Traced it to `[slug]/journal/page.tsx` and `[slug]/journal/[entryId]/page.tsx` still importing `getJournalEntriesBySlug`/`getJournalEntryById` from `mock-journal.ts` — hardcoded fixture data keyed to the `"chika"` demo slug only, exactly the "stand-in... same swap for fetch() later pattern as mock-portfolio.ts" Milestone 9's own comment had promised and Milestone 11 never delivered on for this specific pair of pages (it fixed `mock-portfolio.ts`, which Home/Experience both depend on, and the task got marked done without checking every page that still imported mock data). ## Challenges

- **The RLS policy and the EF Core schema disagreed on column casing.** EF Core defaults to PascalCase column names (`TenantId`); the RLS SQL was written assuming Postgres convention (`tenant_id`). First attempt to apply the RLS script failed with `column "tenant_id" does not exist`. Fixed at the root — added `EFCore.NamingConventions` and `UseSnakeCaseNamingConvention()` — rather than patching the SQL to match PascalCase, since every future hand-written SQL snippet would have hit the same mismatch otherwise.
- **The JWT spike caught exactly what it was designed to catch.** The first real Clerk token came back with an `azp` claim of Clerk's own dashboard origin, not the application's — because `window.Clerk.session.getToken()` was run from the Clerk Dashboard page itself rather than the application's hosted Account Portal sign-in page. Once corrected, the token's `azp` still didn't match the assumed `http://localhost:3000` (that assumption was for testing via a real frontend; testing via Clerk's hosted Account Portal produces a different origin) — config adjusted to match what was actually being tested with.
- **`next build` couldn't be verified end-to-end in the build sandbox** — it tried to download the Linux SWC binary and the sandbox has no network access to `registry.npmjs.org`. Not a real bug: the mounted `node_modules` already has the Windows binary (`swc-win32-x64-msvc`) from Chika's own earlier `npm install`, so `npm run build` on his actual machine uses that directly. Verified what the sandbox could: `tsc --noEmit` and `eslint` both came back clean.
- **A real bug, not just a sandbox quirk: rewriting a file to shorter content didn't truncate it.** Five files that got edited more than once in the same session (`[slug]/layout.tsx`, `AskAiForm.tsx`, `AskAiWidget.tsx`, `Hero.tsx`, `AnthropicLlmProvider.cs`) landed on disk either cut off mid-line or padded with leftover null bytes past the intended ending — confirmed at the byte level (`AnthropicLlmProvider.cs` was exactly its old, longer byte-length, with the tail after the new shorter content zero-filled). Root cause: the edit path wasn't truncating the underlying file to the new content's length when the new content was shorter than what it replaced. Fixed by writing the affected files through a different path (a shell heredoc) that truncates correctly, then verifying byte-for-byte and re-running `tsc --noEmit`/`eslint` clean.
- **PowerShell's `curl` is not curl.** It's aliased to `Invoke-WebRequest`, which doesn't accept curl's `-H` flag at all, producing a parameter-binding error that looked unrelated to auth. Fixed by using `curl.exe` explicitly to reach the real binary.
